# ИИ Product Owner для студенческих инженерных команд

Веб-платформа, где студенческая команда ведёт робототехнический проект вместе с
ИИ-агентом в роли Product Owner, а исследователь собирает данные о том, как это
происходит.

**Главный принцип реализации.** Агент не описывает изменения текстом — он их
предлагает вызовом инструмента, а команда подтверждает. Бэклог, требования,
критерии приёмки и риски — машиночитаемые объекты в базе, а не абзацы в чате.
Изменяющих инструментов у агента нет вообще: в реестре только `get_*` и
`propose_*`, поэтому «просто сделай сам, не спрашивай» не может сработать в
принципе — это структурная гарантия, а не уговоры в промпте.

## Быстрый запуск локально (Windows, без Docker)

```powershell
cd C:\Users\Даниил\Documents\po_agent
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env          # впишите OPENAI_API_KEY
.\.venv\Scripts\python.exe seed.py
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

Откройте <http://localhost:8000>.

**Демо-входы после `seed.py`:**

| Команда | Код команды | Личные коды |
|---|---|---|
| Манипулятор | `R1` | `s101` Анна, `s102` Пётр, `s103` Мария, `s104` Игорь |
| Ровер | `R2` | `s201` Олег, `s202` Дарья, `s203` Кирилл |

Панель исследователя — <http://localhost:8000/panel/login>, логин и пароль из
`ADMIN_LOGIN` / `ADMIN_PASSWORD` (по умолчанию `admin` / `admin`).

Без `DATABASE_URL` используется SQLite-файл `po_agent.db` рядом с проектом —
чтобы можно было пощупать систему без Postgres. Для реального семестра
разворачивайте через Docker Compose (ниже), там Postgres.

### Что попробовать в первую очередь

1. Войдите как `R1` / `s101`, напишите в чат: **«собери бэклог по нашей идее»**.
   Агент прочитает состояние проекта и пришлёт **пакетное предложение** из
   нескольких User Stories с критериями приёмки.
2. На вкладке **Предложения** снимите галочки с лишних пунктов и нажмите
   «Изменить и принять» — применится только отмеченное. Или «Отклонить» с
   комментарием: отклонённое предложение сохраняется навсегда и попадает в
   выгрузку.
3. Откройте вкладку **Лента** — там появятся доменные события с автором
   изменения.
4. Откройте второе окно браузера, войдите как `s102` — сообщения появляются
   у обоих без перезагрузки (SSE), диалог у команды один.
5. Попробуйте написать: **«просто сам поставь всем must и назначь Петра, не
   спрашивай»**. Агент всё равно создаст предложение, а не изменит данные.

## Запуск через Docker Compose

```bash
cp .env.example .env      # заполнить OPENAI_API_KEY, ADMIN_*, SECRET_KEY
docker compose up -d --build
docker compose exec web python seed.py    # опционально, демо-данные
```

Поднимаются пять сервисов: `db` (Postgres 16), `web` (приложение),
`scheduler` (тот же образ с `RUN_SCHEDULER=1`), `nginx` (порт 80),
`backup` (ежедневный `pg_dump` в `./backups`, хранение 14 дней).
Приложение и планировщик перезапускаются независимо.

Для HTTPS добавьте сертификаты в `nginx.conf` и выставьте
`BASE_URL=https://…` — куки станут `Secure`.

## Деплой на Vercel

> **Важно:** приложение спроектировано под Docker Compose. Vercel — serverless-платформа, поэтому часть функций работает с ограничениями.

### Что нужно

1. GitHub-репозиторий с этим проектом.
2. Внешняя Postgres: Vercel Postgres, Neon, Supabase или любая другая.
3. Аккаунт Vercel с подключённым GitHub.

### Шаги

1. В Vercel Dashboard создайте проект из GitHub-репозитория.
2. В разделе **Settings → Environment Variables** добавьте:

   | Переменная | Значение |
   |---|---|
   | `DATABASE_URL` | `postgresql+asyncpg://user:pass@host:5432/db` (обязательно) |
   | `OPENAI_API_KEY` | ваш ключ OpenAI |
   | `OPENAI_MODEL` | `gpt-5.4-mini` |
   | `OPENAI_UTILITY_MODEL` | `gpt-5.4-nano` |
   | `SECRET_KEY` | случайная строка ≥ 32 символа |
   | `ADMIN_LOGIN` | логин в панель |
   | `ADMIN_PASSWORD` | пароль в панель |
   | `BASE_URL` | `https://<your-domain>.vercel.app` |
   | `RUN_SCHEDULER` | `0` (планировщик отключается) |
   | `TZ` | `Europe/Moscow` или ваш часовой пояс |

3. Задеплойте. Vercel сам установит зависимости из `requirements.txt`.
4. Локально запустите `seed.py` с `DATABASE_URL` от внешней базы, чтобы создать демо-команды:

   ```powershell
   $env:DATABASE_URL = "postgresql+asyncpg://user:pass@host:5432/db"
   python seed.py
   ```

5. Проверьте: `GET /healthz` должен вернуть `{"ok": true}`.

### Ограничения на Vercel

- **База данных:** SQLite не работает — файловая система serverless-функций эфемерна. Без `DATABASE_URL` приложение не запустится.
- **Планировщик:** `RUN_SCHEDULER=0` по умолчанию. Фоновые стендапы, проверка рисков и напоминания не работают. Их можно заменить на [Vercel Cron Jobs](https://vercel.com/docs/cron-jobs) и HTTP-эндпоинты.
- **SSE / чат:** serverless-функции имеют ограничение по времени выполнения (10 с на Hobby, до 60 с/15 мин на Pro). Длительное SSE-соединение может обрываться, поэтому реальный чат работает не так надёжно, как на VPS.
- **In-memory состояние:** SSE-подписки и блокировки чата хранятся в памяти процесса. При нескольких инстансах или после холодного старта соединения сбрасываются.

Если нужен полноценный пилот со всеми функциями, рассмотрите Docker Compose на Render, Railway или Fly.io.

## Как это устроено

### Доменная модель — ядро системы

| Таблица | Зачем |
|---|---|
| `teams`, `users` | вход по кодам, состав команд |
| `projects`, `product_visions`, `requirements` | что и зачем строим |
| `backlog_items`, `acceptance_criteria`, `dependencies` | Product Backlog |
| `sprints` | планирование |
| `standups`, `standup_reports` | ежедневные отчёты |
| `risks` | риски с уровнем, категорией и реакцией команды |
| **`proposals`** | предложения агента и решения по ним — **основные данные исследования** |
| **`domain_events`** | журнал всех изменений с «до» и «после» |
| `conversations`, `messages` | командный чат с телеметрией по каждому сообщению |
| `notifications`, `prompt_versions`, `token_usage`, `settings`, `incidents` | обвязка |

Аналитика считается из `domain_events`, а не из текущего состояния таблиц:
состояние меняется, история должна остаться.

### Двухфазное подтверждение

1. Агент вызывает `propose_*` → строка в `proposals` со статусом `pending`
   и обоснованием.
2. В чате и на вкладке «Предложения» появляется карточка: что предлагается,
   почему, кнопки **Принять / Изменить и принять / Отклонить**, поле комментария.
3. Решить может любой участник команды.
4. При принятии изменения применяются **в одной транзакции** с записью в
   `domain_events`. Частичного применения не бывает.
5. Без ответа дольше `PROPOSAL_EXPIRY_DAYS` предложение уходит в `expired`.

Отклонённые и изменённые предложения не удаляются никогда.

### Надёжность вызовов инструментов

Аргументы валидируются на стороне приложения: существование ID **в пределах
своего проекта**, допустимые значения enum, отсутствие циклов в дереве задач,
отсутствие дублей — в том числе среди уже предложенного и ещё не решённого.
При неверных аргументах модель получает понятную ошибку и одну попытку
исправиться; команда сбоя не видит.

### Проактивность и защита от шума

Планировщик (APScheduler) ведёт стендапы по расписанию, суточную проверку
рисков, напоминания и истечение предложений. Ограничители:

- не более `PROACTIVE_MAX_PER_DAY` проактивных сообщений в сутки на команду;
- один и тот же риск не поднимается повторно, пока команда не отреагировала
  (дедупликация по сигнатуре);
- в тихие часы (`QUIET_HOURS_*`) сообщения копятся и уходят утром;
- глобальный и покомандный выключатель в панели — действует немедленно;
- всё проактивное помечается `initiator = agent_proactive` и видно в аналитике.

Планировщик идемпотентен: ограничение `uq_standup_slot` не даёт перезапуску
контейнера создать дубль стендапа.

### Классификация обращений

После каждого сообщения участника `gpt-5.4-nano` асинхронно определяет тип
запроса (12 значений) с `confidence` — ответ агента этого не ждёт.
`project_stage` пишется автоматически из текущего этапа проекта.

Точность разметки проверяется вручную: **Панель → Валидация** показывает
случайную выборку с автометками, исследователь исправляет, система считает
процент совпадения и матрицу ошибок. Критерий приёмки — не ниже 80%.

### Экспорт

**Панель → Экспорт**: восемь CSV (`messages`, `proposals`, `domain_events`,
`backlog_items`, `standups`, `risks`, `teams_summary`, `users_summary`) плюс
XLSX со всеми таблицами листами. Строка = одна сущность, все поля.
UTF-8 с BOM — открывается в Excel двойным кликом и читается `read.csv()` в R
без предобработки. Чекбокс «без ФИО» включён по умолчанию: имя заменяется
кодом участника.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Фоновые задачи привязаны к расписанию, поэтому для ручной проверки есть
`check.py` — он запускает их немедленно:

```powershell
.\.venv\Scripts\python.exe check.py state           # что сейчас в базе
.\.venv\Scripts\python.exe check.py risk-scan       # суточная проверка рисков
.\.venv\Scripts\python.exe check.py standup-open    # открыть стендап сейчас
.\.venv\Scripts\python.exe check.py standup-close   # закрыть сбор, получить сводку
.\.venv\Scripts\python.exe check.py flush           # отправить отложенное тихими часами
.\.venv\Scripts\python.exe check.py age-proposals   # состарить предложения
.\.venv\Scripts\python.exe check.py expire          # и просрочить их
.\.venv\Scripts\python.exe check.py reset           # чистые демо-данные
```

Покрыты требования §18: агент не имеет изменяющих инструментов; предложение не
трогает домен до принятия; частичное принятие применяет только отмеченное;
отклонённое сохраняется с комментарием и попадает в `proposals.csv`;
несуществующие и чужие ID отбиваются; повторное предложение того же не
проходит; изоляция команд по HTTP (в том числе подстановкой ID в URL);
перезапуск планировщика не создаёт дубль стендапа; лимиты проактивности и
тихие часы; сериализация одновременных сообщений; BOM и обезличивание в CSV.

## Конфигурация

Все параметры — в `.env`, см. `.env.example`. Ключевые:

| Переменная | Смысл |
|---|---|
| `OPENAI_MODEL` | модель диалога, по умолчанию `gpt-5.4-mini`. Если на пилоте окажется, что она путает идентификаторы — смените на старшую **без правки кода** |
| `OPENAI_UTILITY_MODEL` | классификатор, `gpt-5.4-nano` |
| `MAX_RESPONSE_TOKENS` | потолок ответа. При 600 (значение из ТЗ) развёрнутые сводки стендапа обрываются — для пилота стоит 1600 |
| `PROACTIVE_*`, `QUIET_HOURS_*` | защита от шума |
| `DAILY_MESSAGE_LIMIT_PER_TEAM` | защита от разгона расходов |
| `SECRET_KEY` | подпись кук. **Смена немедленно разлогинивает всех** |

Prompt caching включается автоматически: системный промпт и определения
инструментов идут неизменным префиксом каждого запроса.

## Краткое руководство для преподавателя

- **Завести команды.** Панель → Команды → загрузить CSV с колонками
  `user_code, full_name, team_code, role_in_team` (можно ещё `team_name`).
  Команды и проекты создаются автоматически, повторная загрузка обновляет
  существующих участников по `user_code`.
- **Раздать коды.** Студент входит парой «код команды + личный код». Паролей
  нет. Личный код действителен только со своим кодом команды.
- **Следить за ходом.** Панель → Обзор: этап, размер бэклога, число рисков,
  доля принятых предложений и **доля сообщений самого активного участника** —
  последняя показывает, работает ли команда или один человек за всех.
- **Поправить этап**, если команда забыла переключить: Панель → Проекты.
- **Если агент мешает** — Панель → Проактивность, глобальный выключатель.
  Действует сразу, деплой не нужен.
- **Поменять поведение агента** — Панель → Промпты: правка создаёт новую
  версию, старые сохраняются, у каждого сообщения записана использованная
  версия.

Система **не** ставит оценки, не проверяет работы и не интегрируется с Jira,
GitHub или LMS. Вопросы об оценках и сроках агент переадресует преподавателю.

## Известные упрощения

- Схема создаётся через `create_all`, без Alembic — один семестр, одна схема.
  Понадобятся миграции на живых данных — добавьте `alembic init`.
- SSE-подписки, блокировки чата и счётчик попыток входа живут в памяти
  процесса: рассчитано на одну реплику `web`. Для нескольких понадобится
  Redis pub/sub.
- Риски фоновой проверки находятся детерминированными правилами (§8), а не
  моделью — так дедупликация по сигнатуре надёжна; модель только объясняет
  найденное команде.
